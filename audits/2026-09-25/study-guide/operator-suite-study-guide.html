Part 1 What the suite asks

The suite is a set of neural operators, each trained on density functional theory (DFT) calculations of crystals, and each judged against simple methods fixed before it trained. Its plan, test-suite.md, was built on 19 August 2026, before any model code existed. For every entry it names the task, the data, how the data is split, the simple methods to beat, and by how much.

What counts as a model here

An operator maps a whole function to a whole function: a field goes in, a field comes out, and the output can be asked for at any point or on any grid. An ordinary neural network maps a fixed list of numbers to a fixed list of numbers. The plan admits only operators. Fixed-vector predictors are excluded whatever their pedigree, and single numbers such as band gaps enter only as read-outs of a predicted function, never as training targets.

The flagship is the example to keep in mind: it takes the charge density on a three-dimensional grid and returns the electron localization field on a grid.

Floors and bars

A floor is a simple method every model must beat: copy the closest training example, fit a straight line, predict the average. Each floor is computed on exactly the runs the model is judged on, before the model trains. A bar is the margin required over a floor, written down in advance, such as "25% better than the ridge floor". Missing a kill bar removes the entry, or that task, and the miss is recorded as a dead end with its evidence.

Because floors and bars exist before training, no threshold can be moved after a result is seen. The audit checked the dates: every judged model's bars were committed before its first training run.

One seed

Each configuration was trained once, from one random seed. On the branch–trunk network's task, a twelve-run seed sweep measured the spread from run to run at 14–35% of the median. A difference of a few percent between two single runs is therefore noise, and the results page says so beside its numbers.

The rules for finishing, and the pause

On 16 September Javier and the PI set the rules: failures are acceptable and are marked as dead ends rather than ground on; one seeded run per configuration; every escalation the plan names is tried once before an entry is called dead; and the two entries without a package each get a minimal build. On 25 September the PI paused all training and model development until what exists is verified. The last training run stopped at 00:18 on 18 September.

Part 2 The raw material: VASP runs

VASP is the program that solved density functional theory for every crystal in this project. Each run is a folder of its output files on /Pool, a separate disk outside the repository. The pool holds 5,085 runs, and the repository never stores any of them.

What one run produces

FileWhat it holdsWhat to remember
CHGCARThe charge density; in a spin-polarized run, the magnetization follows as a second block.It stores density times the cell's volume. The store divides the volume out, giving electrons per cubic ångström.
ELFCARThe electron localization field, from 0 to 1.Written on half the density's grid per axis, so 80³ becomes 40³. No fine-grid localization truth exists anywhere.
LOCPOTThe total local potential, in electronvolts.A periodic cell has no absolute zero of potential, so it is compared after each field loses its own mean.
AECCAR0, AECCAR2The all-electron core and valence densities.Stay summed over spin.
AECCAR1Free-atom densities simply added up: no bonding at all.Serves as a floor: a structure model must beat it.
EIGENVALThe electron energies at each sampled point in momentum space.The density of states is rebuilt from these with a stated smearing, never read from VASP's own density-of-states file.
OUTCAR, OSZICARThe log: electron count, magnetic moment, the element record.Element identity comes from here, never from opening a pseudopotential.
POTCARThe licensed pseudopotential.Never opened, quoted or copied. The repository is public.

Two laws hold across the field files. The half-grid law: the localization field is always on exactly half the density's grid per axis. The spin-block law: in a spin-polarized run every field file doubles, so CHGCAR holds density and magnetization, while ELFCAR and LOCPOT each hold a spin-up and a spin-down field.

Cheap and accurate

Many geometries were computed twice: once with the cheap functional (PBE, or PBEsol for the alloy) and once with the accurate hybrid (HSE), which costs 10–100 times more and places band gaps much closer to experiment. The hybrid mixes in a fraction of exact exchange, and that fraction differs by campaign: 0.27 for the strain atlas, 0.25 for the defect set, 0.325 for the alloy. "Accurate" is therefore a different target in each campaign, and the plan forbids pooling them.

The census and the store

The census, _census/runs.jsonl, has one row per run, derived by parsing the files themselves, never directory names. The store, _derived/, holds one archive per run (5,085 in all) plus a small sidecar recording the census row's hash and the extractor's version. Fields are single precision; scalars and curves are double. Densities are divided by the cell volume. Nothing is standardized in the archives: means and spreads are computed from training folds only, when data is loaded, because statistics baked into the archives would carry test information into every model.

A freshness guard compares every archive with the census before any metric is reported. On 25 September the audit found all 5,085 archives fresh, every charge integral within 2.7e-7 of its electron count, and raw files matching the store to 3–6e-8.

Exclusions

Ten rules, E1 to E10, remove or flag runs before any split. E1 drops a defect triad branch that is a byte copy of another (6 runs). E2 drops a zirconium "accurate" run that is the cheap run's bytes. E6 drops 73 dead relaxation runs. E8 flags 128 perovskite runs with fractional occupancy, for gap labels only; their fields stay usable. The audit re-resolved all ten against the files.

The licensing rule

Nothing volumetric and nothing derived from a pseudopotential leaves /Pool; only metric tables and plots do. That is why the data lives on its own disk and why no model output is ever committed as an array.

Found Defects in the data, confirmed since the models were built

Two silicon-dopant runs name the dopant "H" in every file header, while the log and electron count say silicon. They are the only 2 of 5,085 archives whose labels disagree, and the store inherits the wrong label. It matters for a model keyed by element (the structure-to-density network), not for the flagship.

AECCAR0 and AECCAR1 are written on the starting geometry; the other fields on the relaxed one. The store keeps one geometry per run, so in relaxed runs the core and free-atom densities do not sit on the stored structure. This mixes two geometries into the superposed-atom floor. Pending How far that moves the floor's published numbers is still being verified.

82 of 196 defect runs hold a point where the magnetization exceeds the density, because the stored density can go negative near heavy atoms. The flagship clips this at its input.

Part 3 Splitting the data without cheating

A test score means something only if the model never saw the test examples, or near-copies of them. This corpus is full of near-copies: strains that are the same crystal turned around, two functionals computed at one geometry, folders that are byte copies of each other. So runs are grouped into units that always travel together, and every split assigns units, never single runs.

Orbits

The strain atlas strains a cubic crystal. Swapping two axes, or flipping an axis's sign, maps a strain onto an equivalent one: the same crystal, turned. The code reduces each run's six strain components to a canonical form under the 48 signed axis permutations, and every run sharing that form, under both functionals, belongs to one orbit. The 2,680 strain-atlas runs form 296 orbits. A random split would put one copy of a crystal in training and its turned twin in the test, and the test would measure memory.

The co-split rules

  • Byte-identical copies count once.
  • The cheap and accurate runs of one geometry always land in the same split.
  • The strain atlas and the supercell campaign share one fold map for the 120 shear values they have in common.
  • The alloy splits by configuration, each configuration taking its satellite runs along.
  • Every reported number is labeled interpolation (a held-out point between training points) or extrapolation (outside them).

The four split files

The splits are committed files, and the code regenerates them byte for byte.

Interpolation and extrapolation

Along a sweep, neighboring runs are nearly identical. Holding out a level that sits between two training levels tests interpolation, which a straight line between the neighbors often does almost perfectly. Holding out everything beyond the training range tests extrapolation. The perovskite split adds two extrapolation holdouts: every run with a lattice factor of 0.8, and separately every run with a factor of 1.2.

Found The perovskite split misses a symmetry

The perovskite split makes every run its own unit. But the cell's five atoms sit at the corner, the body center and the three edge midpoints, positions that swapping or reversing the cell's axes leaves unchanged. Reversing one cell edge turns the two angles touching it into their supplements, and 0.8 × 90° = 72° is the supplement of 1.2 × 90° = 108°. Many runs are therefore the same crystal written in a different cell.

Checked on 2 October with my own script. The 125 angle runs are only 14 distinct crystals. Every one of the 25 fold-0 angle runs has a same-crystal run in folds 1–4, and in each "extrapolation" holdout, 57 of the 61 runs are crystals that also sit among the runs not held out. On the fields themselves, pairs predicted to match do, to 2–6e-7 after the axis change (as stored they differ by 0.11–0.30). A genuinely different crystal stays at 8.2e-2 under all 48 axis changes.

Three smaller in-sample problems surfaced in the same checks. None flips a verdict, because each affected model lost even with the advantage.

  • The manifold decoder is compared with leave-one-level-out floors on 423 levels, but 337 of those levels are its own training data.
  • The Galerkin transformer's interpolation comparison scores it in-sample on 24 of 27 levels.
  • The two-input network's fixed bases are fit on folds 1–4, so the validation fold sits inside its own components. Its verdict against its twin is unaffected.

A secondary metric splits the error into low and high Fourier bands.

Found It is not a true per-band relative error. On a test field the same error scores √2 differently when it lies along z instead of x (0.030861 against 0.021822). Over a band covering the whole field it returns 0.296828 where plain relative L2 gives 0.298005.

From runs to one number

Each run gets its error; each unit gets the median of its runs; the result is the median over units. Symmetry copies inside one orbit therefore count once. Weighting by runs would let crowded, easy orbits outvote sparse, hard ones; on the branch–trunk task, aggregating to orbits moved the ridge floor from 0.251% to 0.414%. The interval printed beside a median is a bootstrap over units, but of the mean, not the median, a mislabel the grading deep dive found.

The pass rule

One line of code decides every verdict: improvement = 1 − member ÷ floor. The model passes if its improvement meets the required margin and is killed otherwise. A negative improvement means the floor did better.

Worked example from the perovskite lattice task: a member at 0.0183 against a ridge floor at 0.0423 with a 25% bar has improvement 1 − 0.0183 ÷ 0.0423 = 56.7%, so it passes. The manifold decoder at 0.002452 against bracketing interpolation at 0.000911 has improvement −169.2% against a required 33.3%, so it is killed.

Where the verdicts live

  • Each model's report.md, written by its report.py: the source of truth.
  • results.json: the same rows and verdicts in machine form. Seven models write one; the flagship and the branch–trunk network do not.
  • cross_member.md: one table built from the results.json files, so the flagship has no row on its own task.
  • operator-results.md: the one-page index, kept by hand. Its own words say every number is copied from a report. Its test checks only four rows and passes even when it checks none.

Part 5 Training a model

The engine seam

Every model is written in the project's own code against a small engine interface. A reference engine computes gradients by finite differences and serves as the correctness check; the training engine wraps an existing automatic-differentiation library behind the same interface. Only the operators/substrate package may import that library, and a test fails the build if any other file names it. The plan is to replace the borrowed parts with in-house ones later, behind the same interface, without touching any model.

The card

Training runs on one RTX 2060 graphics card with 6 GB of memory, 5.61 GB of it usable, in single precision. Only one job runs on it at a time: two concurrent trainings measured 2.56 times slower than the same two run one after the other. Evaluation runs on the processor, lowered in priority and pinned to a few cores so it never slows a training run.

How data is fed

  • Whole fields. The flagship takes one run per step: its 80³ density, cut to 40³ before the first layer.
  • Point samples. Models with a coordinate trunk draw a few runs and random points in them at each step, so memory depends on the batch, not the grid, and runs on different grids can mix.
  • Basis coefficients. Models with a fixed basis work on each field's top 32 components.

Inputs and targets are standardized with statistics from the training folds only. Examples: the flagship log-compresses each spin's density; the Galerkin transformer standardizes its target voxel by voxel; the two-input network standardizes its potential coefficients, a fix described in Part 7.

The training loop

  • The loss is mean squared error on standardized targets for fields, and curve L1 for the density of states.
  • The optimizer is the project's own implementation of Adam.
  • Every 100 steps the loop scores each validation unit, averages over units, keeps the best parameters so far, and writes a checkpoint holding parameters, optimizer state, curves and the random state.
  • In the last stage, training stops after 15 validation passes in a row without improvement (patience).
  • A relaunch resumes from the last checkpoint. That mattered: the laptop lost power during runs, and every run now resumes per stage.

The staged schedule

A probe of up to 200 steps at the peak learning rate of 1e-3 checks that the loss stays finite and does not blow up; if it does, the probe reruns at 0.3 times the rate. Then come three stages at the peak rate, one third of it and one ninth of it, over 30%, 30% and 40% of the step budget. Only the last stage stops early.

Found The schedule returns the last stage's best, not the best overall

For the explicit flagship, stage 1 reached a validation score of 8.02e-5 and stage 2 only 8.08e-5. The model evaluated and reported is stage 2's, yet the results page prints 8.0e-5 beside it, which is stage 1's number; the evaluated model's is 8.1e-5. The weight-tied rung lost the same way, by 2.0%.

Budgets against steps actually run

A step budget is fixed in advance, often from a measured cost per step, and early stopping can end a run well before it. The Galerkin transformer's budget was 7,200 seconds ÷ 0.137711 seconds per step = 52,283 steps; it stopped after 33,170 steps plus its probe, in about 78 minutes.

Found The results page reports that budget as the steps it ran in its two hours. Likewise, the two-input network and its twin had budgets of 33,650 steps, and both completed 22,090.

Two older schedules

The branch–trunk network's learned-trunk and energy-trunk runs predate the shared schedule and used their own three stages:

  • the learned trunk ran 6,000, 6,000 and 8,000 steps at 3e-3, 1e-3 and 3e-4;
  • the energy trunk ran 800, 1,200 and 5,000 steps at 2e-3, 7e-4 and 2e-4.

Inspection and figures

A standing rule says everything a model computes, learns or stores must be reachable as named arrays through its Inspect() method, and figures may be drawn only from that interface. Figures render from cached arrays, reproducibly byte for byte, and are committed: 822 of them at the audited commit. The audit re-rendered every component figure from its cache. All matched except one flagship plot, where later code had added a scalar.

Weight-tying wins at matched parameters: the tied rungs beat the single layer 3.4–3.7 times over. It loses at matched width: the twelve-layer stack is still better. What broke
The shared fixed-point code had four defects that surfaced only on its first runs on the card:
  • it asked numpy to read a tensor that lived on the card;
  • its acceleration step ran on the processor;
  • it never fed the input back in, so every input reached the same fixed point and the model could only output a constant;
  • its stopping tolerance was absolute, which on a four-million-entry state meant parts per million.
Then the layer turned out not to contract at its default initialization, so three stability rungs were built. The first, spectral clipping (capping each mode's gain so the map contracts), passed its probe and was trained.

killed

The perovskite angle sweep. Judged on its 25 fold-0 runs and on 27 interior levels of the angle arm.

What broke
Three defects were found and fixed before the verdict:
  • the decoder's queries carried only coordinates, so training made the output blind to the lattice factors (outputs for two structures 27% apart at initialization, 4e-8 apart after training);
  • the electron-count correction sat inside the training loss;
  • the density's spikes at the atomic cores dominated the squared error (the top 5% of voxels carried 77% of it), fixed by standardizing voxel by voxel.
The first gate run is void.
Hypothesis
Recorded before the verdict, never tested: six numbers and four Fourier modes per axis cannot build structure concentrated at atomic cores. The branch–trunk network solves the same task because its basis hands it that structure.
Audit
Re-scored exactly. The interpolation comparison is in-sample on 24 of 27 levels, and the copy floor misses the symmetry copies; the kill stands either way.

Part 8 After the models

The deck

On 18 September a talk deck covered which models failed and why, and proposed a next idea: a learned step placed inside the DFT solver's own loop, checked before it is accepted. That idea is a design only; nothing was built.

The pause

On 25 September the PI stopped all training and model development until what exists is verified.

The grading deep dive

The same day, every grade of the passing models was re-derived from the raw VASP files with separately written readers and scoring code. Every headline, floor and bar of the flagship reproduced to six digits from its checkpoint; the branch–trunk and correction floors reproduced exactly. It found:

  • the silicon dopant labeled "H";
  • the flagship's fold 0 holding three different tests;
  • a run of figure defects:
    • the correction floors figure collapsing five floors into one;
    • error-spread titles counting run-and-spin rows as units;
    • the "mean interval" column bootstrapping the mean, not the median;
    • the flagship's floors figure drawn in relative L2 while its verdicts are in mean absolute error.

The audit

The audit asks three questions of everything in the suite. Is the output right? Are the statements about the output right? Does what was written before the code match what was built?

  • A frozen copy. Auditors read a write-protected copy of the repository at commit 485a7d9. The store and census on /Pool were made read-only, and the pseudopotential files unreadable. These permission locks are still on.
  • Blind auditors. 26 auditors each own a slice of the repository and see nothing of what is already known. Each finding is a contradiction pair: a verbatim quote from the repository beside what contradicts it (a second quote, a command's output, or a physics reference).
  • Severities. S1 wrong result, S2 wrong statement, S3 silent deviation from a pre-code document, S4 latent bug, S5 cosmetic.
  • The ledger. Every checkable promise in the documents written before the code becomes a row, checked against what was built.
  • Re-scoring. Every saved model was scored again from its checkpoint, with no training. Every reported number reproduced at its printed precision.
  • Verification. Each claim is then checked blind, and every wrong result or wrong statement again by me before anything is fixed. Fixes go on a separate branch, and nothing is pushed without Javier's word.

Where it stands on 2 October:

  • 19 auditors returned 552 findings (S1 22, S2 300, S3 73, S4 87, S5 70), and three more saved 91 before the account's session limit stopped them: 643 claims awaiting verification.
  • Four auditors and most of the ledger have still to run.
  • The audit is paused while this guide is written.
